Lanesra OS Agent Playground & Orchestration: Design Specification

Oct 14, 2026 · @Vikram Grover

Summary

Lanesra OS already has most of the building blocks: named agents, a checkpointed execution graph, three pipeline topologies (sequential, consensus and peer review), a tool-call firewall and approvals. This spec adds an Agent Playground and a richer Orchestration layer on top of them. Together they let a business user design, test, run and govern a team of agents against real workspace data, in one place.

We studied CrewAI 1.15.28, Microsoft Agent Framework (core 1.21.0), LangGraph 1.2.15 and AutoGen 0.7.5 to learn which ideas work for builders and where they break in an enterprise setting. We re-implement the ideas, never the code. CrewAI runs one Python process with no permissions model. Lanesra OS will offer the same ease of authoring on top of governance that Lanesra already enforces on every tool call.

What we learned from each framework is in the Research appendix at the end. This document is the product spec; the features we adopted are listed near the end, before the roadmap.

Goals

  1. Playground: a side-by-side workspace where a user can chat with one agent or a whole team, see every reasoning step, tool call, delegation and cost live, and replay or fork any run. Setup uses plain-language settings groups with safe defaults, and an optional Guided Setup takes users from first agent to live orchestration.
  2. Orchestration modes: add Manager-led (dynamic delegation), Graph (DAG with branches and parallel work), Event Playbooks (react to record events), Debate, Round Table (turn-based group discussion) and Handoff (agents pass control directly) modes. These join the existing sequential, consensus and peer-review topologies.
  3. Task contracts: every task declares its expected output, a structured schema, guardrails, a retry budget and the context it may read.
  4. Enterprise context: agents read the Ontology, Object 360, Business Glossary and record-level access, so they act on the business model, not on raw text.
  5. Governance by default: every run is policy-checked, audited, budget-capped, replayable and attributable to a human or service identity.

Non-goals (v1)

  • A general-purpose Python SDK for developers. Lanesra stays no-code-first, with REST, MCP and CLI for automation.
  • Hosting third-party model weights. Bring-your-own-key and Ollama stay the model story.
  • Real multi-worker concurrency on the desktop edition. The Team Workspace server gets it first (see Roadmap).

Clean-room approach

We borrow concepts and behaviour, never code, prompts or file structure. CrewAI, Microsoft Agent Framework, LangGraph and AutoGen are all MIT-licensed, so even copying would be legal with attribution. We still keep a clean room because Lanesra is Rust and TypeScript, its model is different, and its own design will age better.

Rules for the team

  1. Two roles. Analysts read CrewAI, Agent Framework, LangGraph or AutoGen and write behaviour notes in plain language, like the findings in the Research appendix. Implementers build only from this spec and those notes. They never open any of these projects' source while writing Lanesra code.
  2. No prompt reuse. All system prompts, manager personas and ReAct format strings are written fresh and stored in Lanesra's own prompt catalog. CrewAI's phrasing (for example "your job depends on it") is not used. Agent Framework's ledger and speaker-selection prompts are not reused either; Lanesra's progress card has its own wording and schema.
  3. No name or structure mirroring. Lanesra's own vocabulary is used throughout: Team, Playbook, Run and Step, not Crew, Flow, Kickoff, Executor, Superstep, Magentic, StateGraph, Send, Command, Swarm or GraphFlow.
  4. Ideas are free; expression is not. Ideas such as a role/goal persona, a manager who delegates, a composite memory score and a final-answer nudge at the iteration limit are general patterns found in many systems.
  5. Attribution file. If any third-party code is ever pulled in as a dependency, it goes in a THIRD_PARTY_NOTICES entry, as REA already does.
  6. Review gate. Each orchestration pull request carries a short checklist: no copied prompt, no transliterated function, design traced to this spec.

Core concept model

Six objects describe everything: an Agent does work, a Team groups agents under a mode, a Task is a contract for one unit of work, a Playbook wires tasks into a graph, a Run is one execution, and a Step is one node inside a run. Agents, Teams and Playbooks follow the existing Draft → Test → Published → Deprecated → Disabled lifecycle.

Persona fields

A persona has three short fields that business users can fill without prompt-writing skill: Role ("Accounts Receivable Analyst"), Goal ("Recover overdue invoices without harming the relationship") and Background (domain experience and tone). Lanesra compiles these with the instructions, guardrails, memory digest and ontology context into the system prompt. The compiled prompt is visible read-only in the Playground.

Seats

A Team has seats such as Researcher, Drafter, Reviewer and Approver. Tasks are assigned to seats, not agents. Swapping the agent in a seat keeps the playbook intact, and lets an A/B test compare two agents in the same seat.

Context bindings

A Task lists exactly what it may read: step:research.summary, record:{{trigger.record_id}}, knowledge:pricing-policy, memory:team. Each binding has a token budget. Nothing is passed implicitly, which fixes the unbounded raw-text context found in CrewAI.

Orchestration engine

Every mode compiles to one execution graph and runs on the existing graph runtime. That keeps one durability, checkpoint, approval and audit path for all eight modes. A mode is authoring sugar: it picks a graph template and fills it from the Team and its Tasks.

Manager-led mode, done properly

CrewAI's hierarchical process hands every task to one manager, who delegates by role name. Lanesra's version adds a visible plan and hard limits.

The manager never acts on records itself; it plans, reviews and writes the final answer, while seat agents do the work.

  1. Plan. The manager reads the goal, the team's seats and each seat's capability card. It writes a plan as structured JSON: steps, assigned seat, expected output and dependencies. The plan is validated against the schema.
  2. Preview and approve. The Playground shows the plan as a graph with a cost forecast. By default every plan needs human approval before step 1. A Team Owner can relax this to plans above a cost or risk threshold.
  3. Execute. Steps are added to the run as real graph nodes, so they are checkpointed, audited and replayable like any other node.
  4. Check and re-plan. After each step the manager may accept, request a retry with feedback, or re-plan. Re-plans are capped (default 2) and every version of the plan is kept.
  5. Finish. The manager writes the final answer against the Team's output contract.

The manager can only delegate to seats in its own team, chosen by ID. Delegation depth (4) and a fan-out cap per step (default 5) apply.

Progress card. After every round, the manager fills a structured card with five answers, each with a reason: is the goal met, are we looping, are we making progress, which seat goes next, and what instruction it gets. Three "no progress" rounds in a row trigger a re-plan; a "looping" answer twice in a row pauses the run for a human. Cards are shown in the Trace and stored with the plan.

Scheduling and concurrency

  • Team Workspace server: a worker pool runs parallel branches concurrently. Default 4 workers per workspace, set by the admin.
  • Desktop: keeps today's ordered walk of branches. The run trace marks them as "logically parallel" so users are not misled.
  • Fairness: each run holds a budget lease. A run that exhausts it pauses in waiting_budget rather than failing.

Superstep commits. Parallel branches write to a staging area. When every branch of the step has finished, their writes commit together and the checkpoint is taken. If two branches write the same field, the run records a conflict and follows the Join node's conflict rule (first wins, last wins, or ask a human) instead of silently overwriting.

State, checkpoints and replay

The runtime already checkpoints after every node. We add three user-facing actions:

  • Resume a paused or crashed run from its last checkpoint (exists).
  • Replay from step re-runs one step and everything downstream, reusing upstream outputs unchanged.
  • Fork copies a run up to a chosen step into a Playground session, so the user can change a prompt, model or tool and compare the two branches side by side.

Run outputs are immutable. A replay or fork always creates a new run linked to its parent.

Where orchestration lives

Teams replace Pipelines as the thing people build, but a Team does not run itself. Orchestration is three parts in the shared Rust core (desktop/core):

  • a compiler that turns a Team's mode, seats and Tasks into an execution graph;
  • the existing graph runtime, which runs that graph;
  • a new run controller, which owns start, pause, budget, replay and fork.

Because all three live in desktop/core, the desktop app, the Team Workspace server, REST, MCP and the CLI all run exactly the same orchestration.

How a Team run happens

  1. Trigger. Run in the Playground, a schedule, a webhook, a workflow action or a record event.
  2. Admit. The run controller loads the Team's published version, resolves the acting identity, checks the budget and shows a forecast.
  3. Compile. The compiler turns the mode into a graph, cached per Team version. Dynamic modes (Manager-led, Round Table, Handoff) compile to a small fixed graph whose plan or selector node adds steps while the run is going.
  4. Execute. The graph runtime walks the nodes and checkpoints after each one. Agent nodes call the agent loop; approval nodes pause into the approvals inbox.
  5. Close. Events stream to the Playground and the audit log. The controller writes outputs and cost, then fires any downstream triggers.

Retiring Pipelines

  1. First release with Teams: every existing Pipeline converts to a Team automatically. Sequential, consensus and peer review map one-to-one onto modes. Triggers and run history are relinked, and the Pipelines screen becomes read-only with a link to its Team.
  2. Compatibility: Pipeline REST endpoints, the admin assistant's run_ai_agent_pipeline tool and Pipelines inside Solution exports keep working as aliases that run the Team.
  3. Two releases later: the aliases are removed after a deprecation notice. Pipeline tables stay read-only for audit history.

Agent runtime loop

One loop runs every agent step: Lanesra's existing run_agent_once_with_text, extended rather than replaced. Each round streams a trace event, every limit ends in a graceful state, and each output is checked against its Task contract before the step completes.

Round structure

  1. Assemble context. Compile the persona, instructions, guardrails, memory digest, ontology context pack and bound inputs. Trim each binding to its token budget. Record what was included and why (the "context receipt").
  2. Call the model through the AI Gateway: per-step model routing, fallback chain, and forced air-gap if any bound data is classified sensitive.
  3. Tool calls. Use native function calling when the provider supports it, else a strict JSON tool format (not free-text ReAct). Each call goes through the firewall: schema, permission, policy, approval, execute, audit.
  4. Emit a trace event per round: tokens, cost, latency, tool calls and their verdicts, sent over the existing SSE stream.
  5. Repeat until the model returns a final answer or a limit is hit.
  6. Validate output. Check against the output schema, then run guardrails. On failure, return the reasons to the agent and retry within the retry budget.
  7. Persist. Write step output, memory updates (through the memory policy) and the audit record.

Each tool binding adds three limits of its own: calls per step, failures before the tool is switched off for that step, and the largest result kept in context (larger results are stored and referenced, not pasted).

Reasoning modes

  • Direct (default): answer with tools as needed.
  • Plan-first: the agent writes a short plan, shown in the trace, before acting. This is useful for long tasks.
  • Reflect: after a draft, the agent critiques it against the expected output once before submitting. This costs about one extra model call per step.

Prompt hygiene

Lanesra's prompt catalog is written fresh, uses calm instructions, and states the output contract plainly. No prompt threatens or pressures the model. Prompt templates are versioned assets, so a change is diffable and goes through evaluation like an agent version.

Hook points and compaction

Policies and guardrails attach at three points in the loop: around the whole step, around each model call, and around each tool call. Admins configure them as Policy objects; no code is needed.

Each agent also has a compaction policy for long histories: drop the oldest turns, keep a recent window, prune old tool calls, or shorten tool results. The default is to shorten tool results first, then keep a recent window.

Tools, connectors and MCP

Agents use one tool catalog from four sources, and every tool carries a risk tier. The Tool Registry already classifies native, connector and MCP tools into six tiers (read, low write, write, external action, destructive, privileged). This spec adds team-level tools and better tool cards for the Playground.

Tool sources

  • Native: record CRUD, search, reports, Action Types from the Ontology ("Reassign Company Owner").
  • Connectors: OpenAPI-imported connectors from the Integration Hub. Read-only by default; write needs a per-connector opt-in.
  • MCP servers: external servers registered as Connections, with tools discovered via tools/list. They are read-only by default, with a two-level gate for writes.
  • Team tools (new): handoff_to_seat, ask_seat, post_to_board (a shared scratchpad for the run) and request_human_input. Each is a registered tool with its own risk tier.

Tool card

Each tool shows a card in the Playground and the agent editor: name, plain-language purpose, input schema, risk tier, data classes touched, connector or server of origin, average latency and cost, and the last 5 calls with verdicts.

Memory and knowledge

Memory recall ranks by a weighted mix of meaning, freshness and importance, and every item carries a scope and a data class. Lanesra already has session, working and entity memory with classifications. This spec adds composite ranking, a team scope and automatic extraction under policy.

Scopes

Scope Lifetime Who reads it
Run board (new) One run Every agent in the run
Session One conversation That agent
Working TTL set per agent That agent
Team (new) Until deleted Every agent seated on the team

Recall ranking

Each candidate gets a score from three signals: how close it is in meaning to the current task, how recent it is (exponential decay with a half-life per scope), and its importance (set by the agent or an admin when saved). Weights are set per team, with sensible defaults. Where no embedding provider is set, the FTS5 search score stands in for semantic match. The Playground shows why each memory was chosen.

Writing memory

  • Explicit writes through remember (exists).
  • Auto-extraction (new, opt-in): after a step, a small model call suggests facts and entities worth keeping. Suggestions go through the memory policy: sensitive and restricted classes need approval or are dropped.
  • Every write records its source step, so deleting a run can cascade to the memories it created (right to erasure).

Knowledge

Knowledge Collections stay as they are: chunked, embedded and always cited. Tasks bind collections explicitly. The Playground shows each cited chunk inline, so a reviewer can check every claim against its source.

Setup experience and Guided Setup

Anyone who can describe a job in plain words should be able to build an agent, a team and its orchestration without reading this spec. Two things make that possible. Every setting lives in a few plain-language groups with safe defaults. An optional Guided Setup walks the whole journey, shows where you are and what is left, and can be opened or closed at any time.

Principles

  1. Plain words first. Labels describe the outcome (“Who can this agent act for?”), not the mechanism (“Record scope”). Technical names appear only in tooltips.
  2. Works with three fields. A new agent runs once it has a name, a job description and one tool. Everything else starts from the template or workspace defaults.
  3. Essentials, then More options. Each group shows only its essentials. Advanced settings fold away behind a one-line summary such as “Defaults: 8 rounds, $2 cap”.
  4. One home per setting. Each setting is edited in exactly one place; other screens show it read-only with a link to its home.
  5. Say what a change does. Each change shows its effect in one sentence (“Any record update will now need approval”), and the risk and cost badges update live.
  6. Optional never blocks. An untouched optional group shows “Using defaults”, never an error. Only Publish has hard requirements.

Guided Setup

The guide is a lens over the real object, not a separate wizard: each stage's status is read from the agent or team itself, so edits made anywhere count.

Open it any time, close it any time.

  • A Guide me button sits in the header of the agent, team and canvas editors and in the Playground. It is also in the command palette, and the admin assistant opens it when asked (“help me set up a collections team”).
  • The guide opens as a side panel next to the editor, so the user always works on the real screen.
  • Closing it keeps progress. Users can switch it off for themselves; an admin can make it open by default for Builders.

Where you are and what is left.

  • A progress rail shows the six stages. Each stage shows one status: Done, In progress, Using defaults, Needs attention (with a count) or Not started.
  • The current stage is highlighted, and a “What’s left” list names each open item with a link straight to the field.
  • Stages can be visited in any order. The only enforced gate is Publish: it needs the safeguards stage reviewed and at least one passing test run.

Each step teaches as it goes.

  • One sentence on why the step matters, then the recommended value filled in, with a Use recommended button.
  • Show me an example opens the same step from a matching template.
  • A check turns green as soon as the step is satisfied.

Three ways to start.

  1. Describe it. The user writes the job in plain words, for example “chase overdue invoices politely and escalate disputes”. Lanesra drafts the agents, team, steps and mode as a Draft, and the guide walks the user through reviewing each part.
  2. From a template. The guide opens with stages 1 to 3 prefilled and points to what must be customised.
  3. From blank. Every stage starts empty, with defaults ready.

Pick up where you left off. Unpublished drafts show a “Continue setup” banner with the percentage done. Progress is saved per object, so a colleague who opens the draft sees the same state.

Help choosing a mode. Stage 3 asks up to three plain questions instead of listing eight mode names: Do you know the steps in advance? Do the agents need to discuss? Should one agent coordinate the others? The answers recommend a mode, show a small picture of how it works, and allow switching later without losing tasks.

Agent Playground UX

The Playground is where a team is built, tried and proven before it is published. It has three panes: Build on the left, Conversation in the centre, and Trace on the right. A run started anywhere in Lanesra (schedule, webhook, workflow) can be opened here, read-only, in the same view. The Playground ships in both the desktop app (including Team Workspace) and the online demo. The demo runs on sample data in the browser, with write tools always simulated.

Panes

  • Build: pick an agent or team, edit settings in the same groups as the editors (see Setup experience), with Guided Setup available as a side panel. Unsaved edits apply only to Playground runs.
  • Conversation: a chat or a structured input form generated from the playbook's input schema. A test record can be bound with a record picker ("run against Invoice INV-000231").
  • Trace: a live timeline of steps, rounds, tool calls, delegations, guardrail verdicts, approvals and memory reads and writes. Each item shows tokens, cost and latency. Clicking an item opens its full payload and the context receipt.

Key interactions

  1. Plan preview. Before a Manager-led or Graph run, show the planned graph and cost range (low to high), then wait for Run.
  2. Step-through. Optionally pause after each step: inspect, edit the output, then continue. This is useful for teaching and debugging.
  3. Simulate writes. A toggle runs write-tier tools against a rollback transaction and shows a before-and-after diff per record.
  4. Compare. Run the same input on two variants (prompt, model, seat assignment or mode) side by side, with a diff of outputs, cost and latency.
  5. Fork and replay. From any step: "Fork here" opens a new branch; "Replay from here" re-runs downstream steps.

  7. Promote. "Publish team" runs the linked suite first. Publish is blocked if the pass rate is below the team's threshold (default 90%).

Enterprise governance

Every run acts as a named identity, under a policy, within a budget, and leaves a complete audit trail. This is Lanesra's main edge over CrewAI, which has no permission model. All of it reuses the existing dispatch: schema → permission → policy → approval → execute → audit.

Identity

  • Interactive runs act as the user who started them, intersected with the agent's ontology scope. An agent can never see more than its user.
  • Unattended runs (schedule, webhook, workflow) act as an Agent Identity: a service principal with its own Access Role and Record Scope. This replaces today's requirement that unattended admin-scoped runs resolve to a real Administrator.
  • Every step records both the agent and the effective identity.

Enterprise sign-in (OIDC and SAML) is built first, in phase 1. Users, approvers and Agent Identities then all map to the customer's own directory.

Policy controls (extending AiAgentPolicy)

  • Approval threshold by risk tier (exists), plus plan approval for every Manager-led plan, on by default.
  • Output guardrails as policy objects: PII leak check, tone, required disclaimer, schema conformance, an allow-list of external domains.
  • Data boundaries: which data classes may reach which model provider. Sensitive data is forced onto local models (exists in the gateway).
  • Four-eyes rule: a run's starter cannot approve that run's own privileged steps.
  • Kill switch: an AI Admin can pause all runs of a team or the whole workspace instantly. Runs enter paused and resume cleanly.

Approvals

All pause-for-human points move onto the durable ai_approvals inbox. This retires the three older mechanisms noted in ai_orchestration_service. Approvals carry context (plan, diff and evidence), SLA timers, escalation to a backup approver, and mobile-friendly approve or reject.

Cost control

  • A cost forecast before each run, from the plan's step count and each model's token history.
  • Budgets at workspace, team, run and step levels, in both USD and tokens. Every workspace starts with a default monthly AI budget; only an AI Admin can raise it.
  • Monthly cost reports by team, agent, model and business unit (using the existing Org Units).

Audit and compliance

  • An append-only, hash-chained audit log per run: prompts, model outputs, tool inputs and outputs, verdicts, approvals.
  • Configurable retention and redaction: tool audit records are kept 7 years for all customers, and step outputs 90 days by default.
  • Evidence export: a signed bundle (JSON plus PDF summary) of one run, for regulators or customers.
  • Deleting a run cascades to its derived memories, and records an erasure entry.

Deployment and residency

The desktop edition stays fully offline-capable with Ollama. Team Workspace adds per-workspace model-provider allow-lists and region pinning. No telemetry leaves the workspace by default; OTLP export goes only to an endpoint an admin sets.

Observability and evaluation

Every run is traceable step by step, and no team version reaches Published without passing its evaluation suite. Both build on parts Lanesra already has: OTLP tracing on runs and the Evaluation Harness.

Trace model

  • Span tree: a run contains steps, a step contains rounds, and a round contains model calls and tool calls. Delegations nest as child steps.
  • Span attributes: agent version, model, provider, tokens in and out, cost, latency, policy verdicts, guardrail verdicts and the context receipt hash.
  • Live channel: span events stream over /api/v1/events/stream to the Playground.
  • Export: OTLP to any collector an admin configures. Prompt and output bodies are excluded unless the admin enables it per team.

New capabilities this spec adds

  1. Round Table mode. Several seats discuss in turns. The next speaker is chosen by a rule, round-robin or the manager. The run stops on a termination rule or a round cap.
  2. Handoff mode. Seats pass control to each other directly, as in a support desk, with no central manager. An admin-edited routes matrix limits who may hand to whom, and a turn cap applies (default 30).
  3. Progress card. In Manager-led mode, every round the manager answers five fixed questions in structured form: done yet, looping, making progress, who next, and what instruction. Three "no progress" rounds in a row force a re-plan. The card is shown in the Trace.
  4. Content labels by default. Every value in a run carries a trust label (trusted or untrusted) and a confidentiality label taken from Lanesra's data classes. Combining values keeps the strictest labels. Write-tier and external tools refuse untrusted inputs unless a policy allows them; untrusted text can be summarised by a model with no tools before an agent sees it.
  5. Missions. A long-running run where the agent keeps a visible todo list, may start background sub-runs, and loops until the list is empty, its budget runs out or a human stops it. Useful for month-end close or a data clean-up.
  6. Superstep commits. Parallel branches write to a staging area; writes commit together when all branches of a step finish. Two branches writing the same field is flagged as a conflict in the Trace rather than silently overwritten.
  7. Canvas type-checking. Before Publish, every connection is checked: each Task's output schema must satisfy the next Task's input binding.
  8. Context compaction policy. Each agent picks how its history shrinks when long: drop oldest, keep a recent window, prune tool calls or shorten tool results. The Playground shows tokens saved.
  9. Progressive skills. Agents see only skill names and one-line purposes until they load one, which keeps prompts small.
  10. Sandboxed code tool. Python and SQL in an isolated sandbox with no network by default, at the Privileged risk tier.
  11. Open interop (v2). Teams callable from other systems over A2A; Playground events available over AG-UI; teams exportable as a declarative YAML document inside a Solution.

Delta features from the deeper study

A second pass through Agent Framework surfaced 13 capabilities this spec lacked. Lanesra adds them in its own form, plus 4 that neither framework has. Each item names its source and its roadmap phase.

Orchestration

  1. Teams as building blocks (from sub-workflows and workflow-as-agent). A published Team can fill a seat in another Team or be a node in any graph. When a child team needs an approval, the parent can answer it within its own policy or pass it up to a human. Depth counts toward the delegation cap of 4. Phase 3.
  2. Plan and Execute modes per agent (from agent operating modes). In Plan mode an agent may only call read-tier tools and must produce a plan. Switching to Execute requires the user or a policy to approve. This makes "look before you act" a product rule, not a prompt habit. Phase 3.
  3. Background model calls (from continuation tokens). Long provider calls, such as deep-research models, run in the background. The run waits in a new waiting_model status, survives a restart and resumes when the result is ready. Phase 4.
  4. Safe expressions in Playbooks (from the declarative expression language). Conditions, routes and transforms use one expression language shared with Business Rules. It has hard limits (nesting depth, value count and text size) so a bad expression fails clearly instead of hanging a run. Phase 3.

Approvals and safety

  1. Standing approvals (from tool-approval rules). An approver can choose "always allow this tool" or "always allow it with these arguments". The choice is scoped to a run, a team or the workspace and expires after a set period (default 30 days). Every standing rule is listed, auditable and revocable in one place. Phase 1.
  2. Approval bound to exact arguments (from argument-change detection). An approval covers the exact arguments shown to the approver. If a retry, guardrail or policy changes any argument, the call needs approval again. Phase 1.
  3. Per-tool caps (from invocation limits). Each tool binding can set the maximum calls per step, the maximum failures before the tool is disabled for that step, and the maximum result size kept in context. Phase 1.
  4. Gate on server-initiated MCP requests (from MCP sampling controls). When an external MCP server asks Lanesra's model to generate text or asks the user a question, the request is denied by default. If an admin allows it, it goes through the approvals inbox with per-server caps on requests and tokens. Phase 1.

Memory and context

  1. Memory consolidation (from the memory harness). A scheduled job reads recent run transcripts, extracts durable facts into topic notes with an index, and merges duplicates. The agent's owner sees a diff and approves it before it lands. Restricted-class content is never extracted. Phase 4.
  2. Team drive (from shared file access). Each Team has a file area its agents can list, read, search and edit. Files are stored as Lanesra attachments, carry content labels, and every edit is versioned. Search has a time limit. Phase 3.

Outputs, interop and quality

  1. Interactive output cards (from generative UI). Agents can return cards built from Lanesra's own components: record card, field-edit form, approval form, table and chart. Cards are checked against a schema and retried on failure. A user can act on a card in place, and each action goes through the normal write path. Phase 2.
  2. Team as an endpoint (from the developer server's OpenAI-compatible API). Each published Team can be exposed as an OpenAI-compatible chat endpoint and as an MCP tool, using scoped API keys. External apps can then call a governed Team without knowing Lanesra. Phase 4.
  3. Deeper team evaluation (from workflow evaluation). Suites run each case N times to measure variance, score every seat separately as well as the whole Team, and check tool arguments, not just which tools were called. Phase 2.

Beyond both frameworks

  1. Shadow mode. A new Team version runs alongside the published one on real triggers, with every write simulated. The two versions' outputs, costs and verdicts are compared for a set period before promotion. Phase 4.
  2. Impact analysis before Publish. Lanesra's System Graph shows which Teams, Workflows, Solutions and Action Types depend on the agent or team being changed, and which evaluation suites will rerun. Phase 2.
  3. Outcome metrics. A Team links to Business Glossary metrics, such as invoices recovered or leads qualified. Dashboards then show business results per run and per dollar spent, not just tokens. Phase 4.
  4. Organisation-aware approval routing. Approvals route by record owner, owning Org Unit and Work Team, with out-of-office fallback, using the ownership model Lanesra already has. Phase 3.

From LangGraph

Sixteen additions not yet in this spec. Each is redesigned for business users and governance.

State and flow

  1. Field merge rules. A Playbook's run state is a schema edited in the UI. Each field picks how parallel writes combine: keep latest, append to list, sum, union, keep highest-confidence, or ask a human. This replaces the generic conflict rule in superstep commits with an explicit choice per field. Phase 3.
  2. For-each step. One node runs a seat once per item in a list, such as every overdue invoice, with a concurrency cap, a per-item timeout and a merge step. Partial failures are listed per item, and the step can retry only the failed ones. Phase 3.
  3. Agent-chosen next step. In Graph mode, an Agent node may choose the next node and update state in one decision, but only among targets the author ticked. Every choice is logged with its reason. Phase 3.
  4. Run-at-end nodes. A node can be marked to run once all other branches finish, for summaries, notifications or clean-up, even if some branches failed. Phase 3.
  5. Do-not-persist fields. A state field can be marked memory-only: it is never written to checkpoints, traces or audit, so tokens and sensitive values do not linger. Resuming such a run re-fetches the field from its source. Phase 1.
  6. Delta checkpoints. Checkpoints store only what changed, with a full snapshot every 20 steps. This keeps SQLite on the desktop small for long Missions. Phase 4.

Human review and repair

  1. Four review responses. Each approval can allow any of: Approve, Edit then approve, Reply with feedback (the agent tries again) and Skip this step. The author picks which are allowed per gate. Phase 1.
  2. Side-effect-safe resume. When a step resumes after a pause, writes it already made are recognised by idempotency key and not repeated. This fixes the re-run-from-start hazard. Phase 1.
  3. Breakpoints on live runs. An AI Admin can set a breakpoint on a node of a published Team. Matching runs pause there for inspection, then continue. Breakpoints expire after 24 hours by default. Phase 2.
  4. Edit state and resume. From any checkpoint, an authorised user can correct a field and resume as a new branch. The edit, its author and the reason are audited, and the original branch stays intact. Phase 2.

Reliability and cost

  1. Durability per Team. Choose save-every-step (default, required when the team writes records), save-in-background for read-only teams, or save-at-end for Playground drafts. Phase 3.
  2. Retry with backoff per node. Transient failures such as rate limits and timeouts retry with backoff and jitter (default 3 attempts). Policy and validation errors never retry. Phase 1.
  3. Identity-aware step cache. Read-only steps can cache results for a set time. The cache key includes the inputs, the acting identity's access scope and the data version, so a cached answer never leaks across users or survives a record change. Phase 4.
  4. Budget awareness. Each agent turn is told how many steps, tokens and dollars remain, so agents wrap up gracefully instead of hitting a hard limit. Phase 1.

Runs as a service

  1. Busy-run policy. Each Team sets what happens when new input arrives during a run: reject, queue, interrupt and merge, or cancel and restart. For record-triggered Teams, duplicate events for the same record are merged by default. Phase 3.
  2. Team variants. One Team can have named variants, such as by region or business unit, that change only settings: model, thresholds, prompt text, approvers. Variants are versioned and evaluated together, so logic is maintained once. Phase 3.

Beyond all three

  1. Record lineage. Every record change an agent makes appears on that record's own activity timeline, linked to the run, step, agent version and approver. No framework can do this because none owns the business records. Phase 2.
  2. Stream levels and progress events. Clients subscribe at one of four levels: summary, steps, tokens or debug. Tools can emit progress events such as "40 of 200 invoices checked". Playground streams resume after a tab is closed and reopened. Phase 2.

From AutoGen

Fourteen additions, each redesigned for business users and governance.

Orchestration control

  1. Stop rules you can compose. A Team ends when a rule built in the UI is met, combining conditions with AND and OR: number of turns, a phrase or result appears, token or cost spent, time elapsed, a named seat speaks, a handoff to a person, a specific tool is called, or someone presses Stop. Every run records which rule ended it. Phase 3.
  2. Wait for all, or for any. In Graph mode, a step's incoming connections can be grouped. Within a group the step waits for all or for any, for example “after the data is fetched, and once legal approves or finance waives”. The canvas checks that groups are consistent before Publish. Phase 3.
  3. Who may speak next. Round Table gains three settings: an eligibility rule that narrows the candidates for each turn, a switch for whether the same seat may speak twice in a row, and an optional fixed rule that overrides the manager's choice. Phase 3.
  4. What a nested team returns. When a Team fills a seat in another Team, its owner picks what flows back: the final answer only, a model-written summary of the inner discussion, or the full transcript. The inner team starts fresh on each call unless memory is switched on. Phase 3.
  5. What each seat sees. In conversational modes, each seat has a visibility rule, such as “the user's first message and the Researcher's last message”. This cuts tokens and stops seats seeing data they do not need. Phase 3.
  6. Keep the start and the end. History trimming gains a head-and-tail option that keeps the first messages and the most recent ones. It suits tasks where the original brief must never be lost. Phase 1.

Governance and scale

  1. Inspect agent-to-agent messages. Policy hooks extend to messages between agents (delegations, handoffs and Round Table turns), not just model and tool calls. An admin rule can redact, block or log them, so data-loss rules apply inside a team as well as at its edges. Phase 3.
  2. Team events. A Team can publish a named business event, such as “dispute raised”, and other Teams can subscribe to it, with the same permission checks as record events. Teams then cooperate without hard-wired links. Phase 4.
  3. Remote workers. On Team Workspace, chosen seats can run on a registered worker machine, for example a GPU box with local models or a server inside the network zone that holds the data. Workers connect with mutual TLS and appear in the Trace like any step. Phase 4.
  4. Notebook sandbox. The sandboxed code tool gains a stateful session per run, so a data-analysis agent keeps variables between steps. Code is shown to a reviewer before it runs when policy requires. Phase 4.

Quality and reuse

  1. Recorded runs for tests. Any Playground or production run can be saved with its model responses. Test suites replay them at no model cost and with identical results, so changes to orchestration logic, routing or guardrails are tested deterministically. Phase 2.
  2. Test button on everything. Every model, tool, connector, agent, team and stop rule has a one-click test that reports in plain words what worked and what did not. Guided Setup uses these checks to mark steps green. Phase 1.
  3. Lessons from corrections. When a reviewer uses Edit then approve, Lanesra proposes a short lesson, such as “Always cite the contract clause number”. The agent's owner approves or rejects it. Approved lessons are recalled on similar future tasks, and each one links back to the correction that created it. Phase 4.
  4. Workspace gallery. A browsable gallery over Solutions lets builders reuse approved agents, tools, stop rules and whole Teams from colleagues with one click. Each entry shows its owner, version and evaluation score. Phase 3.

Roadmap and decisions

The Playground (phase 2) ships before new modes, so teams can be tested on today's pipelines first. Durations are a proposal, to be confirmed in planning against team size.

Each gate must pass before the next phase starts. Phase 1 is mostly backend work on the existing runtime; phase 4 targets Team Workspace first and the desktop edition later.

Delta features land as marked. Phase 1 adds standing approvals, argument-bound approvals, per-tool caps and the MCP request gate. Phase 2 adds output cards, deeper evaluation and impact analysis. Phase 3 adds nested teams, Plan and Execute modes, safe expressions, the team drive and organisation-aware routing. Phase 4 adds background calls, memory consolidation, team endpoints, shadow mode and outcome metrics.

LangGraph deltas land as marked too. Phase 1 adds do-not-persist fields, the four review responses, side-effect-safe resume, retry with backoff and budget awareness. Phase 2 adds live breakpoints, edit-and-resume, record lineage and stream levels. Phase 3 adds field merge rules, for-each steps, agent-chosen next steps, run-at-end nodes, durability per Team, the busy-run policy and Team variants. Phase 4 adds delta checkpoints and the identity-aware step cache.

AutoGen deltas land as marked. Phase 1 adds head-and-tail trimming and the test button. Phase 2 adds recorded runs for tests. Phase 3 adds stop rules, all-or-any waits, speaker rules, nested-team returns, seat visibility, agent-to-agent message hooks and the gallery. Phase 4 adds team events, remote workers, the notebook sandbox and lessons from corrections.

Setup experience lands early. Settings groups for agents ship in phase 1. Guided Setup ships in phase 2, covering agents and today's pipeline topologies. Phase 3 extends both to Teams, every mode and the canvas.

Appendix — Research: what we learned from CrewAI, Agent Framework, LangGraph and AutoGen

Findings from reading each project's MIT-licensed source in October 2026. The design commitments that came out of them live in the main spec tab.

What CrewAI teaches us

CrewAI wins on authoring speed: a role, a goal, a task and a process type get a team running in minutes. It is weak on governance, determinism and cost control, which is exactly where Lanesra is already strong. Findings below come from reading CrewAI 1.15.28 (PyPI, Oct 2026).

Area What CrewAI does Weakness for enterprise Lanesra's better answer
Team process Two modes only: sequential and hierarchical. A third, consensual mode is still a TODO. Hierarchical just sends every task to one manager agent. There is no planning graph, so cost and path vary per run. Eight modes on one durable graph engine, with the chosen plan shown before execution.
Manager agent A built-in "manager" persona whose only tools are delegate work and ask a question. Coworkers are matched by role-name string; two similar roles collide. Delegation recursion has no depth cap at the crew level. Delegation targets agent IDs. Lanesra's existing depth guard (4) and per-run fan-out caps apply.
Task context Earlier task outputs are joined as raw text into the next prompt. Context grows without bound and carries no structure or provenance. Typed step outputs with JSON schemas, explicit context bindings and a token budget per binding.
Agent loop Native tool calls if the model supports them, else text ReAct parsing. Default limit 25 iterations, then a forced final answer. Overflow either summarises silently or exits the whole process. Per-step limits on rounds, tokens, cost and time, plus a graceful "partial result" state that is visible in the run.
Guardrails A function or plain-language rule checks each task output, with retries. Checks are local code, not policy, and leave no audit record. Guardrails are Policy objects: versioned, audited, reusable across agents, with an LLM-judge or rule-based checker.
Tools Python tools, MCP adapters, and a result_as_answer short-circuit. No permission model. Any tool an agent holds can be called with any argument. Every call goes through schema, permission, policy, approval, execute and audit, using risk tiers that already exist.
Memory One unified store. Recall ranks by a weighted mix of semantic match, recency (half-life decay) and importance. An LLM pulls out entities when saving. Memory is per-process; scoping and data classification are thin. Composite recall, plus Lanesra's session, working and entity scopes, sensitivity classes and air-gap routing.
Flows Event-driven Python methods (start, listen, router, and/or joins) with persisted state and human feedback. Code-only, so business users cannot author or review it. Event Playbooks on the visual canvas, triggered by record events, schedules or webhooks.
Testing crew.test() runs N times and scores with an LLM; train() collects human feedback. Results are console output, not a regression suite. Lanesra's Evaluation Harness with golden cases, gating the Draft to Published lifecycle.
Observability An event bus, OpenTelemetry spans and a hosted tracing product. Telemetry goes to the vendor by default (opt-out env vars). Local OTLP plus in-product run timelines. Nothing leaves the workspace unless an admin configures an exporter.

Patterns worth adopting (re-expressed)

  • A persona built from role, goal and backstory is easy for business users to fill in.
  • Iteration limits should end in a final-answer request rather than an error.
  • Tasks should describe their expected output, not only their instruction.
  • Async tasks that join at the next synchronous step are a simple mental model for parallel work.
  • Ranking memory by a weighted mix of relevance, recency and importance beats plain vector search.
  • Checkpoint and replay from any task lets a user fix a step and re-run only what follows.

Anti-patterns to avoid

  • Prompts that pressure the model ("your job depends on it").
  • Exiting the host process when context overflows.
  • Matching agents by free-text role names.
  • Raw string concatenation as the only way to pass context.
  • Vendor telemetry switched on by default.

What Microsoft Agent Framework teaches us

Agent Framework is the strongest engineering base in this space: a typed, checkpointed workflow engine plus five ready-made multi-agent patterns. It is a developer SDK, though, with no business data model, no no-code authoring and few enterprise defaults switched on. Findings come from reading the MIT-licensed Python packages agent-framework-core 1.21.0, -orchestrations 1.3.1, -devui, -declarative, -a2a and -ag-ui (PyPI, Oct 2026).

Area What Agent Framework does Gap for Lanesra's users Lanesra's better answer
Workflow engine Graph of typed executors run in Pregel-style supersteps. Messages move along edges; shared state is staged and committed only at each superstep boundary. It checkpoints after every superstep and stops at 100 supersteps by default. Code-only. Last write wins when two parallel executors write the same state key. Keep Lanesra's graph runtime, add superstep commits for parallel branches, and flag same-key write conflicts in the Playground instead of silently picking one.
Edge types Single, fan-out, fan-in, switch-case and multi-select edges; edges are type-checked against what each executor accepts when the graph is built. Type errors surface to developers, not to business authors. Validate on the canvas: a Task's output schema must match the next Task's input binding before Publish.
Human in the loop Any executor can raise a typed request and the workflow pauses until a response arrives; this survives checkpoints. Tools can be marked "always require approval". Approvals have no inbox, SLA or routing; the host app must build them. The durable approvals inbox, with routing, SLAs, escalation and four-eyes.
Sequential and Concurrent Sequential passes one shared conversation down a chain. Concurrent broadcasts the input to all agents, then an aggregator merges results. Similar to CrewAI and Lanesra's existing pipelines. Already covered by Sequential and Consensus modes.
Group chat A central orchestrator picks the next speaker with a pluggable selection function until a termination condition holds. Selection logic is code. New Round Table mode: speaker selection by rule, round-robin or a manager, set in the UI.
Handoff No central manager: agents pass control by calling a handoff tool that names the next agent. Optional user input after each turn; autonomous mode is capped at 50 turns by default. Any agent can hand to any listed agent; no policy on who may hand to whom. New Handoff mode, with an allowed-routes matrix the admin edits and a turn cap.
Magentic A manager keeps a task ledger (facts and plan) and a progress ledger. Each round it answers five structured questions: is the request satisfied, are we in a loop, is progress being made, who speaks next, and what to tell them. After 3 stalls it re-plans. Ledgers are internal; users cannot read or edit them. Lanesra's Manager-led mode adopts a visible ledger: a progress card per round in the Trace, with stall and loop counts.
Middleware Three interception points: around the agent run, around each model call, and around each tool call. An experimental agent-hooks bundle maps eight lifecycle hooks onto them. Developers write middleware in code. Policy hooks at the same three points, configured as Policies and Guardrails, not code.
Prompt-injection defence Experimental information-flow labels: every piece of content is marked trusted or untrusted and public, private or user-only. Labels combine to the most restrictive. Untrusted text can be held as a variable reference and read only through a quarantined model call. Policy middleware blocks tools in an untrusted context. Opt-in, experimental, and developer-configured. Content labels on by default, mapped onto Lanesra's existing data classes, enforced in the Tool-Call Firewall.
Context and memory Sessions with pluggable history stores and context providers; four compaction strategies (truncation, sliding window, tool-call pruning, tool-result compaction). Memory scope and data classification are left to the developer. Lanesra's scoped memory plus a context-compaction policy per agent, chosen in the Playground.
Agent harness Loop-until-done middleware, a todo list the agent maintains, background sub-agents, agent modes, and file memory. Limits: 40 model round trips by default plus caps on tool calls and duration. Good primitives, no UI. Long-running "Mission" runs with a visible todo list and background sub-runs (see Better than all three in the spec).
Code execution Optional sandboxed code tool on Hyperlight micro-VMs, with allowed domains and file mounts. Separate install, developer-configured. Sandboxed Python and SQL tool at the Privileged tier, read-only by default.
Skills Progressive disclosure: the agent sees only skill names at first and loads a skill's full instructions and resources on demand. File-based. Lanesra's Skills library gains progressive loading to save tokens.
Declarative and interop YAML workflow definitions (stable) and YAML agents (experimental); A2A protocol for agent-to-agent calls across systems; AG-UI for streaming agent events to front ends; DevUI, a local debug web app. Developer tooling, not an end-user product. Solutions export as a versioned declarative format; A2A and AG-UI endpoints in v2. The Playground is the end-user DevUI.
Evaluation Provider-agnostic evaluate_agent, local keyword and tool-call checks for CI, and Microsoft Foundry evaluators. Cloud evaluators tie to Azure. Local judge models through the AI Gateway; no cloud required.
Telemetry OpenTelemetry instrumentation on by default; prompt and response content off by default; data goes only to an exporter the developer configures. Sound defaults. Same stance: matches Lanesra's existing local OTLP design.

Patterns worth adopting (re-expressed)

  • Staging shared-state writes and committing them together at a step boundary makes parallel work predictable and checkpoints consistent.
  • Type-checking connections when a graph is built catches wiring errors before the first run.
  • Asking a manager the same few structured questions every round is a cheap, reliable way to detect loops and stalls.
  • Letting agents hand off control directly suits customer-service style flows better than a central manager does.
  • Tracking whether content is trusted and how confidential it is through the whole run is the most promising defence against prompt injection.
  • Showing an agent only skill names until it needs a skill keeps prompts small.

What LangGraph teaches us

LangGraph is the most precise state machine of the three: every field of a run's state has a merge rule, any node can pause for a human, and any past checkpoint can be edited and resumed. Like Agent Framework, it is a developer library; its server adds run queues and versioned configs. Findings come from the MIT-licensed langgraph 1.2.15, langgraph-checkpoint 4.3.0, langgraph-prebuilt 1.1.0 and langgraph-sdk 0.4.7 (PyPI, Oct 2026).

Area What LangGraph does Gap for Lanesra's users
State A typed state object; each field declares how parallel writes merge (append, add, last value, custom). Some fields are never checkpointed or last only one step. Merge rules are code.
Dynamic fan-out A routing function can send N copies of a node, each with its own input, then merge results (map-reduce). No business-level "for each record" step.
Routing from a node A node can return a state update and the next node in one command, including jumping to its parent graph. Unrestricted jumps are hard to govern.
Human in the loop interrupt() anywhere pauses the run; a resume value continues it. The prebuilt review offers accept, edit, respond and ignore. Breakpoints before or after any node. Node re-runs from its start on resume, so side effects before the pause repeat unless the developer guards them.
Time travel List every checkpoint, edit state as if a given node wrote it, and resume as a fork. Developer API only.
Durability Three modes: save before each next step, save while the next step runs, or save only at exit. One global choice per run.
Node policies Per-node retry (backoff, jitter, max 3 attempts by default), timeout and result cache with TTL. Cache keys ignore who is asking.
Step budget Default recursion limit of 10,007 steps; the prebuilt agent tracks remaining steps (25 by default) so it can wrap up. The budget is in steps, not money.
Streaming Seven stream modes: full values, updates, tokens, custom progress, checkpoints, tasks and debug. Streams can be resumed after a disconnect. Clients must pick and parse modes.
Server runs Versioned configs of one graph ("assistants"); four policies for a new message while a run is busy: reject, enqueue, interrupt or roll back; cron and completion webhooks. Hosted service; policies are per request.

Lanesra's answers to these gaps are the LangGraph items in the spec's delta features.

What AutoGen teaches us

AutoGen is the most research-driven of the four: an actor-style runtime where agents exchange messages over topics, five team types, and a rich library of stop conditions. Its Studio is a no-code builder, but its own package notes say it is not meant for production. Findings come from the MIT-licensed autogen-core, autogen-agentchat and autogen-ext 0.7.5 and autogenstudio 0.4.2.2 (PyPI, Oct 2026).

Area What AutoGen does Gap for Lanesra's users
Runtime Agents are actors with IDs; they publish to topics and subscribe by type or prefix. A single-process runtime, plus a gRPC runtime that spreads agents across processes and machines. Intervention handlers can change, log or drop any message in flight. Powerful but developer-only; no governance on what flows between agents.
Team types Round-robin, Selector (a model picks the next speaker; optional filters on who may speak and whether the same agent may speak twice), Swarm (handoffs), GraphFlow (a directed graph whose nodes wait for all or any incoming edges, by activation group) and Magentic-One. Speaker rules and graph conditions are code.
Stop conditions Eleven condition types: stop message, max messages, text mention, token usage, handoff, timeout, external stop, source match, text message, function call and custom. They combine with AND and OR. No UI to compose them; no record of why a run stopped.
Agent types Assistant, code executor (with an approval callback before running code), user proxy, “society of mind” (an inner team that answers as one agent, summarised by a model) and a message filter (an agent sees only chosen messages from chosen sources). Wrappers are code-only.
Context Buffered (last N), head-and-tail (first N and last M) and token-limited message windows. One more trimming option than this spec had.
Memory List, vector (Chroma, Redis, mem0) and a versioned text canvas agents edit with patches. An experimental task-centric memory stores task-to-insight pairs and recalls them on similar tasks, so agents learn from corrections. Experimental, no review step before an insight is kept.
Code execution Local, Docker, stateful Jupyter kernels and Azure container sessions. Isolation is the developer's job.
Testing A replay model client returns recorded responses in order, so tests run without real model calls; a response cache. Recording and replay are manual.
Studio Drag-and-drop team builder, component gallery, a one-click test for each model, tool, agent, team and stop condition, LLM judges and a playground. Prototyping tool; no permissions, approvals or audit.

Lanesra's answers to these gaps are the AutoGen items in the spec's delta features.
